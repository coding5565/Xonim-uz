# Финансовый калькулятор кафе

Веб-приложение для владельца или финансового директора кафе: вводим параметры заведения —
получаем полную финансовую модель, P&L, точку безубыточности, расчёт целевой прибыли и
симулятор «что будет, если».

Валюта — узбекский сум (`125 000 000 сум`), настраивается в параметрах бизнеса.
Все данные хранятся локально в браузере, бэкенд не нужен.

## Запуск

```bash
npm install
npm run dev      # разработка
npm run build    # production-сборка в dist/
npm test         # тесты движка и рендера страниц
```

## Режим Xonim

Внутри системы Xonim калькулятор собирается в режиме `xonim` и живёт на том же сайте
по адресу `/planner/`. Отдельного входа нет: работает сессия Xonim, а открыть
калькулятор может только суперадмин. Финансы и зарплаты из Xonim в браузере не
сохраняются — модель загружается заново при каждом открытии, поэтому на общем кассовом
компьютере её не достать и из localStorage.

```bash
npm run dev:xonim     # разработка: порт 5174, /api → Xonim на 127.0.0.1:8000
npm run build:xonim   # сборка для сервера Xonim (base /planner/)
```

Исходные цифры приходят из `GET /api/v1/finance/planner/` — факты выбранного месяца
(по умолчанию последнего полного). Как они раскладываются в модель, описано в
[`src/xonim/toModel.ts`](src/xonim/toModel.ts). Коротко: блюда — по средней цене меню
и замороженной себестоимости, скидки и бонусы — отдельной строкой расходов, гости = чеки,
зарплата — по табелю, комиссии Uzum и Yandex, списания и закупки «Masalliq» — % от
выручки, остальные расходы — постоянные. Операционная прибыль сходится с чистой
прибылью Xonim с точностью до двух названных разниц — зарплата по табелю вместо
выплат и поставки партнёрам; сверка показана в «Параметрах бизнеса».

Сценарии (ручки симулятора) сохраняются всегда. Ручные правки самой модели живут до
закрытия вкладки: пока она открыта, фоновое обновление их не стирает — свежие данные
ждут, пока их не примут явно. Чтобы сохранить правки надолго, выгрузите модель в JSON.

## Главный принцип: один движок расчёта

Все финансовые формулы живут в [`src/core/engine.ts`](src/core/engine.ts). Компоненты интерфейса
не считают ничего — они отображают то, что вернул `calculate(model, adjustments)`. Поэтому любое
изменение (цена блюда, стоимость ингредиента, ещё один официант, рост аренды, комиссия эквайринга)
автоматически пересчитывает всю цепочку показателей, и одна и та же величина нигде не может
разойтись между экранами.

```
src/core/       модель данных и расчёты (без React)
  types.ts        доменные типы
  period.ts       нормализация периодов
  units.ts        единицы измерения и перевод в базовые
  format.ts       форматирование сумм и процентов, безопасное деление
  engine.ts       ЕДИНЫЙ расчёт: P&L, KPI, безубыточность, цель
  defaults.ts     демонстрационная модель
src/store/      состояние (zustand + localStorage) и хуки доступа к расчёту
src/pages/      экраны
src/components/ примитивы интерфейса и общая тема графиков
src/i18n/       словари трёх языков и ядро мультиязычности
```

Канонический период расчёта — **месяц**. Любой другой период получается масштабированием
(`scaleTotals`): «объёмные» величины (выручка, затраты, гости, заказы) умножаются на коэффициент,
относительные (проценты, средний чек) остаются неизменными.

## Мультиязычность

Интерфейс доступен на русском, узбекском (латиница) и английском. Переключатель — в шапке
и в параметрах бизнеса.

Русский словарь [src/i18n/ru.ts](src/i18n/ru.ts) — источник истины: его ключи задают тип `TKey`,
поэтому пропущенный или переименованный ключ в узбекском либо английском словаре не доживает
до запуска — это ошибка компиляции.

Множественное число берётся из `Intl.PluralRules`, а не из самодельных правил: в русском три
формы (1 гость, 2 гостя, 5 гостей), в английском две, в узбекском одна. Числа и суммы
форматируются по языку — `125 000 000 сум`, `125 000 000 soʻm`, `125,000,000 UZS` — и поле ввода
разбирает введённое обратно по правилам того же языка: в английской локали «12,5» это 125,
потому что запятая там разделяет разряды.

Переводится только интерфейс. Названия блюд, сотрудников и расходов — это ваши данные:
смена языка их не трогает. Демонстрационная модель создаётся на том языке, который активен
в момент её загрузки. Обозначение валюты подставляется по языку, пока вы не задали своё
в параметрах бизнеса.

## Как нормализуются периоды

Длительности заданы в **рабочих днях**, а не в календарных:

| Период | Длительность |
| ------ | ------------ |
| День   | 1 |
| Неделя | `рабочих дней в неделю` |
| Месяц  | `рабочих дней в месяц` |
| Год    | `рабочих дней в месяц × 12` |

Правило «неделя × 4» сознательно не используется: при 26 рабочих днях и 6-дневной неделе
`1 500 000 сум/неделя` превращается в `1 500 000 × 26 / 6 = 6 500 000 сум/месяц`, а не в 6 000 000.
Год при этом равен ровно двенадцати месяцам, поэтому недельные суммы не «теряют» четыре недели в год.

## Два режима продаж

Активен ровно один режим — выручка двух режимов никогда не складывается.

**По меню.** Выручка и себестоимость собираются по позициям:
`выручка = Σ (цена × продажи)`, `COGS = Σ (себестоимость × продажи)`.
Продажи вводятся в любом периоде, остальные пересчитываются автоматически.
Количество гостей выводится из проданных позиций: `гости = блюда ÷ позиций на гостя`.

**По среднему чеку.** `выручка = гости в день × средний чек × рабочих дней`,
`COGS = выручка × Food Cost %`. Быстрое моделирование без заполнения меню.

В обоих режимах `заказы = гости ÷ гостей на чек`.

## Себестоимость блюда

Либо вводится вручную, либо собирается из технологической карты. Стоимость ингредиента приводится
к базовой единице (г / мл / шт):

```
стоимость базовой единицы = цена закупки ÷ количество в базовых единицах
```

`95 000 сум/кг → 95 сум/г`, значит 180 г говядины стоят 17 100 сум.

Потери (необязательное поле) считаются через выход годного продукта, а не наценкой сверху:

```
эффективная стоимость = стоимость ÷ (1 − потери)
```

При потерях 10% из килограмма остаётся 900 г полезного продукта, поэтому грамм стоит `95 ÷ 0,9 = 105,6 сум`.

Изменение закупочной цены мгновенно меняет себестоимость всех блюд, где используется ингредиент.

## Структура P&L

```
  Выручка
− Себестоимость проданных блюд (COGS)
= Валовая прибыль
− ФОТ
− Переменные операционные расходы
= Операционный результат до постоянных расходов (Contribution)
− Постоянные расходы
= Операционная прибыль
```

Итоговый показатель называется **операционной прибылью**, а не «чистой»: налоги, проценты,
амортизация и прочие статьи ниже операционной прибыли в модель не заведены.

## Постоянные и переменные расходы

Переменный расход считается одним из четырёх способов:

| Способ | Формула | Пример |
| ------ | ------- | ------ |
| % от выручки | `выручка × доля базы × процент` | эквайринг 1% от 70% выручки |
| На заказ | `сумма × количество заказов` | упаковка 4 000 сум |
| На гостя | `сумма × количество гостей` | расходники 1 500 сум |
| Фиксированная сумма | приводится к месяцу по периодичности | прочие 5 000 000 сум/мес |

## Точка безубыточности

Ключевой момент — что считать переменным. **Периодичность выплаты и экономическое поведение
расхода — разные вещи**: оклад, который платят ежедневно, всё равно остаётся постоянным расходом,
потому что не исчезает при падении трафика. Поэтому ФОТ по умолчанию входит в постоянную нагрузку,
а помечать сотрудника переменным нужно осознанно. Так же и фиксированная сумма из раздела
переменных расходов ведёт себя как постоянная. Поведение любого сотрудника и любого переменного
расхода переопределяется вручную.

```
Переменные затраты    = COGS + переменная часть ФОТ + переменные операционные расходы
Постоянная нагрузка   = постоянные расходы + постоянная часть ФОТ + фиксированные суммы
Contribution Margin   = выручка − переменные затраты
CM Ratio              = Contribution Margin ÷ выручка
Break-even Revenue    = постоянная нагрузка ÷ CM Ratio
Гостей до нуля        = Break-even Revenue ÷ средний чек   (в месяц и в день)
Заказов до нуля       = Break-even Revenue ÷ средний заказ
Запас прочности       = выручка − Break-even Revenue       (в сумах и в %)
```

## Целевая прибыль

```
Required Revenue     = (постоянная нагрузка + целевая прибыль) ÷ CM Ratio
Required Guests      = Required Revenue ÷ средний чек        (в месяц и в день)
Required Orders      = Required Revenue ÷ средний заказ
Required Avg Check   = Required Revenue ÷ текущее число гостей
```

Раздел показывает разрыв с текущим состоянием и четыре способа его закрыть: больше гостей,
выше средний чек, ниже себестоимость, меньше постоянных расходов.

## Симулятор и сценарии

Симулятор меняет гостей, средний чек, цены и продажи блюд, Food Cost, закупочные цены, зарплаты,
количество сотрудников, постоянные и переменные расходы. Ручки не изменяют исходные данные —
они образуют сценарий, который накладывается на модель при расчёте. Поэтому «Текущий» сценарий
всегда остаётся эталоном, а любая правка при активном «Текущем» автоматически уходит в «Свой сценарий».

Готовые сценарии — «Текущий», «Оптимистичный», «Пессимистичный», «Свой», плюс любые собственные.
Страница сравнения считает их все одновременно и показывает разницу по прибыли.

## Тесты

`npm test` проверяет движок на примерах из технического задания (экономика плова, техкарта бургера,
потери, нормализация недельной зарплаты, выручка режима среднего чека), сходимость P&L,
корректность безубыточности и целевой прибыли, а также рендер всех тринадцати экранов — в том числе
на пустой модели, где легко получить деление на ноль.

Отдельный набор проверяет переводы: совпадение набора ключей во всех трёх словарях, отсутствие
пустых строк, сохранность подстановок вроде `{count}` в каждом переводе, выбор правильной формы
множественного числа и формат чисел по языку. Все тринадцать экранов рендерятся на каждом из трёх
языков с проверкой, что в интерфейс не просочился сырой ключ или незаполненная подстановка.
